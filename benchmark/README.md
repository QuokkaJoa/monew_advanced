# 댓글 조회 성능 측정

어떤 조건에서 어떻게 쟀는지 적어둔다. 결과는 재고 나서 여기에 붙인다.

## 측정 구간

| 구간 | 인덱스 | 캐시 | 분산락 | 보려는 것 |
|---|---|---|---|---|
| A | 없음 | 끔 | - | 원래 얼마나 느렸나 |
| B | 있음 | 끔 | - | 인덱스로 얼마나 해결되나 |
| C | 있음 | 켬 | 끔 | 캐시만으로 충분한가 |
| D | 있음 | 켬 | 켬 | 분산락이 무엇을 막았나 |

**분산락이 효과가 있다고 미리 정해두지 않는다.** 인덱스를 넣으면서 DB 조회가 빨라졌다. 그래서 C와 D가 같게 나올 수도 있다. 같게 나오면 같다고 적는다.

## 구간 바꾸는 법

구간을 바꿀 때마다 아래를 순서대로 한다. **하나라도 빠지면 앞 구간 상태가 섞인다.**

```
1. Redis 비우기
2. 인덱스 켜거나 끄기
3. 환경변수 바꾸고 앱 다시 띄우기
4. 요청 한 번 보내서 200 과 totalElements 확인
5. 워밍업 1분
6. 측정
```

**1번을 빼먹기 쉽다.** 앞 구간의 캐시가 남아 있으면 히트율이 엉킨다. 구간 C와 D는 특히 그렇다. 캐시가 이미 차 있으면 재생성이 안 일어나서 분산락이 뭘 막는지 볼 수 없다.

### 1. Redis 비우기

```bash
# 로컬
docker exec redis-server redis-cli FLUSHALL

# AWS
redis-cli -h <ElastiCache 기본 엔드포인트> FLUSHALL
```

### 2. 인덱스

```bash
# 지우기
psql ... -c "DROP INDEX IF EXISTS idx_comments_article_created"

# 만들기
psql ... -f benchmark/03-index.sql
```

`create_tables.sql` 이 인덱스를 같이 만든다. 테이블을 새로 만든 직후는 **구간 B 상태**다. 구간 A부터 재려면 먼저 지워야 한다.

### 3. 환경변수와 앱 다시 띄우기

```
CACHE_ENABLED=false                          # 구간 A, B
CACHE_ENABLED=true CACHE_LOCK_ENABLED=false  # 구간 C
CACHE_ENABLED=true CACHE_LOCK_ENABLED=true   # 구간 D (기본값)
```

### 4. 응답 확인

```bash
curl "http://<주소>:8080/api/comments?articleId=aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee&limit=10" \
  -H "Monew-Request-User-ID: 00000000-0000-4000-8000-000000000001"
```

화제 기사는 `totalElements` 가 **2843**, 롱테일 기사는 **284** 여야 한다. 데이터를 새로 만든 직후 기준이다.

롱테일 기사는 `10000000-0000-4000-8000-000000000500` 같은 11번 이후 번호로 부르면 된다.

쓰기를 섞은 실행 뒤에는 이 값이 늘어나 있다. 그러면 데이터를 다시 만들고 시작한다.

### 5. 워밍업 1분

앱을 다시 띄우면 자바가 아직 코드를 빠르게 만들지 않았고 DB 연결도 다 안 만들어졌다. 1분을 먼저 돌리고 **그 결과는 버린다.**

이걸 빼면 구간마다 예열 상태가 달라서 비교가 깨진다.

## 로컬에서 돌리는 순서

### 1. DB 띄우기

```bash
docker run -d --name idxtest \
  -e POSTGRES_PASSWORD=test -e POSTGRES_USER=monew -e POSTGRES_DB=monew \
  -p 5433:5432 postgres:15

psql -h localhost -p 5433 -U monew -d monew -f create_tables.sql
psql -h localhost -p 5433 -U monew -d monew -f benchmark/01-generate-data.sql
```

### 2. Redis 띄우기

```bash
docker run -d --name redis-server -p 6379:6379 redis:7.0
```

### 3. 앱 띄우기

`.env`를 쓰되 아래 값은 바꿔서 쓴다.

```bash
set -a; source .env; set +a

export DB_PORT=5433 DB_REPLICA_PORT=5433 DB_PASSWORD=test
export SPRING_JPA_HIBERNATE_DDL_AUTO=none
export SPRING_SQL_INIT_MODE=never

./gradlew bootRun --args='--spring.profiles.active=local'
```

바꾸는 이유는 이렇다.

- `DB_PORT` — `.env`에 적힌 5432는 다른 컨테이너가 쓰고 있다. 측정용 DB는 5433이다.
- `DB_REPLICA_PORT` — `local` 프로필은 DB를 두 개 찾는다. 잴 때는 둘 다 같은 DB를 보게 한다.
- `DDL_AUTO`, `SQL_INIT_MODE` — 안 바꾸면 앱이 뜰 때 테이블을 지우고 새로 만든다. 넣어둔 50만 건이 날아간다.

앱이 떴는지 확인한다.

```bash
curl "http://127.0.0.1:8080/api/comments?articleId=aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee&limit=10" \
  -H "Monew-Request-User-ID: 00000000-0000-4000-8000-000000000001"
```

### 4. 부하 주기

환경변수는 꼭 `-e`를 붙여서 넘긴다. 셸에 export만 해두면 k6가 못 읽는다.

```bash
# 짧게 확인만 (약 50초)
k6 run -e START_RATE=10 -e WRITE_RATE=1 -e RAMP=5s -e STEP_HOLD=5s k6/test3.js

# 제대로 재기 (약 12분 30초).  결과를 두 형태로 남긴다
OUT=~/monew-monitoring/results/local-C-limit
k6 run -e START_RATE=250 -e WRITE_RATE=0 \
  --summary-export=$OUT.json \
  k6/test3.js 2>&1 | tee $OUT.txt
```

`$OUT.txt` 는 사람이 읽는 것이고 `$OUT.json` 은 기계가 읽는 것이다.
JSON 에는 계단별 `p95` 와 요청 수가 그대로 들어 있어서 손으로 옮겨 적지 않아도 된다.

**경로를 변수에 담는 이유가 있다.** `--summary-export=~/어디` 라고 직접 쓰면 물결표가 안 풀려서
`~` 라는 이름의 폴더가 생긴다. 변수 대입(`OUT=~/...`)에서는 풀린다.

| 변수 | 기본값 | 설명 |
|---|---|---|
| `BASE_URL` | `http://127.0.0.1:8080` | 때릴 주소. AWS에서는 ALB 주소를 넣는다 |
| `START_RATE` | 100 | 첫 계단에서 초당 몇 건을 보낼지. 여기서 1, 2, 4, 8, 16배로 다섯 계단 올린다 |
| `WRITE_RATE` | 0 | 초당 댓글을 몇 건 쓸지. 0이면 읽기만 한다 |
| `RAMP` | 30s | 다음 계단으로 올리는 데 걸리는 시간 |
| `STEP_HOLD` | 2m | 계단 하나를 버티는 시간 |
| `PRE_VUS` / `MAX_VUS` | 500 / 3000 | 미리 만들어둘 가상 사용자 수와 최대치 |

구간마다 시작값을 다르게 준다. 맥북에서 미리 재보고 정한 값이다.

```
구간 A  START_RATE=50  STEP_MULS=1,1.5,2,2.5,3   맥북에서 초당 138건에서 막혔다
구간 B  START_RATE=250                             맥북에서 초당 2,794건에서 막혔다
구간 C  START_RATE=250                             맥북에서 초당 4,002건까지 한계를 못 찾았다
구간 D  START_RATE=250                             맥북에서 초당 3,574건.  다만 부하 생성기가 오염됐다
```

위 값은 모두 2026-09-25 와 09-27 에 **새 데이터**로 잰 것이다.
그 전에 적혀 있던 `구간 A 초당 128건` 과 `구간 B 초당 1,900건` 은 기사당 댓글이 1.9만 개이고
`comments_like` 가 비어 있던 옛 데이터 기준이라 지웠다.

AWS 는 장비가 달라서 숫자가 다르게 나온다. 위 값은 어디서부터 올릴지 정하는 용도다.

**AWS 는 더 낮게 나올 것이다.** 구간 A 와 B 는 DB CPU 가 병목이고(구간 A 에서 앱 CPU 는 5.4% 였다)
맥북은 코어 10개를 DB 가 쓸 수 있는데 `db.r6g.large` 는 2 vCPU 다.
코어 수로만 줄이면 구간 A 가 초당 28건, 구간 B 가 초당 559건 근처다. (추론)
구간 C 는 DB 를 거의 안 쓰고 앱이 일하므로 `c6g.large` 2 vCPU 기준 초당 2,500건 근처로 본다. (추론)
첫 계단에서 값이 나오면 그 자리에서 사다리를 고친다.

## 데이터 가정

숫자는 `01-generate-data.sql` 맨 위에 모여 있다. 한 줄만 고치면 바꿀 수 있다.

```
화제 기사    10개     댓글 3,000 개    (활성 2,843)
롱테일      990개     댓글   300 개    (활성   284)
총 댓글            327,000 개  (활성 309,790)
좋아요             350,000 개
사용자             100,000 명
트래픽      화제 10개에 80%,  롱테일 990개에 20%
```

### 왜 이 숫자인가

2026-09-25 에 실제 포털을 직접 확인했다.

```
네이버 댓글 많은 뉴스,  언론사 75개,  각 1위 기사       400 ~ 1,700 개
  집계 기준 오후 3시~6시.  그 시점까지의 누적 총합
네이트 뉴스 댓글순 주간 1위,  7일 누적                       1,659 개
네이트 뉴스 댓글순 일간 1위                                   892 개
```

공개 통계도 참고했다. SBS 가 네이버와 다음의 `많이 본 기사` 20만 8천 개와 댓글 1억 9천만 개를 분석한 자료다.
https://news.sbs.co.kr/news/endPage.do?news_id=N1006153616

```
상위 기사 평균                537 ~ 913 개
9개월간 댓글 1개만 쓴 사람      31%
10개 이하만 쓴 사람             75%
상위 10% 작성자가 쓴 비중       70%
```

뉴스는 수명이 짧아 다음 날로 크게 넘어가지 않는다. 저녁까지 더 쌓이는 것만 감안해
**관찰 최댓값 1,700 의 약 1.8 배인 3,000 개**를 화제 기사의 댓글 수로 잡았다.

**기사 한 건당 최다 댓글 기록은 공개된 것이 없다.** 검색과 문서 확인으로 찾지 못했다.

### 작성자 분포

사용자 번호를 9제곱으로 치우치게 뽑아 실제 모양에 맞췄다.

```
댓글 1개만 쓴 사람     10,990명     전체 댓글의  3.4%
2~10개                 24,065명     전체 댓글의 25.1%
11~100개                3,269명     전체 댓글의 22.1%
100개 넘게                177명     전체 댓글의 49.5%
```

**177명이 전체의 절반을 쓴다.** 상위 10%가 72.8%로 실제 70%와 가깝다.
`10개 이하 91%`와 `평균 8.5개`는 실제(75%, 19.5개)와 다르다. 댓글 수 대비 사용자 수 비율이 달라서다.
**세 쿼리 어디에도 작성자로 거르는 것이 없어 측정에는 영향이 없다.**

### 좋아요

30만 건을 전체에 하나씩 뿌리고 5만 건을 화제 기사 최신 11개씩(모두 110개)에 몰았다.

```
화제 기사 최신 댓글 110개    댓글 하나에 456명
나머지 댓글                  댓글 하나에 0.92명
```

무작위 독자가 자기가 누른 댓글을 보게 될 확률은 약 5% 다.

## 맥북에서 미리 재본 결과

AWS 본측정이 아니다. 시작값을 정하려고 돌려본 것이다. **AWS 결과와 같은 표에 넣지 않는다.**

데이터는 모두 같다. 화제 기사 10개 3,000개, 롱테일 990개 300개, 댓글 327,000건(활성 309,790), 좋아요 350,000건.
사다리도 같다. 읽기 커넥션 풀은 따로 적지 않으면 50이다.

| 구간 | 도달 처리량 | 잰 날 |
|---|---|---|
| 인덱스 없음 | 초당 138건 | 2026-09-27 |
| 인덱스만 | 초당 2,794건 | 2026-09-25 |
| 인덱스만, 풀 100 | 초당 2,896건 | 2026-09-25 |
| 인덱스 + 캐시 | 초당 4,002건, p95 21.99ms. **한계를 못 찾음** | 2026-09-25 |
| 인덱스 + 캐시 + 분산락 | 초당 3,574건. **마지막 계단은 못 쓰는 값** | 2026-09-25 |

**인덱스를 넣으면 초당 138건이 2,794건이 된다. 20배다.**
그 20배가 어디서 오는지도 설명된다. 커넥션을 쥐고 있는 시간이 364.8ms 에서 18.36ms 로 19.9배 줄었고,
풀 크기가 양쪽 다 50이라 `풀 ÷ 쥔 시간` 이 그대로 처리량이 된다.

풀을 50에서 100으로 키운 것은 3.6% 만 늘었다. 쥐고 있는 시간이 18.36ms 에서 37.7ms 로 같이 늘어서다.
**줄이 앱에서 DB 안으로 옮겨갔을 뿐이다.**

분산락은 재생성 11,993번 중 473번(25번에 1번)을 막는 대가로
초당 2,000건에서 평균 응답을 2.6ms 에서 9.7ms 로 만들었다. **이 조건에서는 손해다.**

### 인덱스가 없을 때 계단별 (2026-09-27)

| 계단 | 초당 요청 | 앱 응답 | 커넥션 쥔 시간 | 커넥션 쓰는 중 | 줄 선 최대 | 앱 CPU |
|---|---|---|---|---|---|---|
| 50 | 50 | 33.9ms | 32.5ms | 1.2 | 0 | 1.1% |
| 75 | 75 | 44.6ms | 43.4ms | 3.0 | 0 | 2.0% |
| 100 | 100 | 58.7ms | 57.0ms | 5.8 | 0 | 2.9% |
| 125 | 125 | 102.7ms | 101.0ms | 12.4 | 0 | 4.2% |
| 150 | 138 | 1,440.7ms | 364.8ms | 49.8 | 149 | 5.4% |

**앱 응답 시간의 98% 가 DB 커넥션을 쥐고 있는 시간이다.** 앱이 실제로 하는 일은 2ms 안쪽이고
무너질 때도 앱 CPU 는 5.4% 다. 서버를 늘려도 이 문제는 안 풀린다.

무너지는 지점도 계산과 맞는다. `커넥션 50개 ÷ 쥔 시간 364.8ms = 초당 137건` 이고 실측이 138건이다.

부하가 늘수록 쥐고 있는 시간이 늘어난다(32.5 → 364.8ms). 인덱스가 없으니 요청마다 표를 처음부터 끝까지
읽고, 여러 요청이 동시에 훑으면 서로 디스크와 CPU 를 빼앗는다.

캐시만 켠 상태의 계단별 값이다.

| 계단 | 초당 요청 | 앱 응답 | 앱 CPU | 커넥션 쓰는 중 | 줄 선 최대 |
|---|---|---|---|---|---|
| 250 | 250 | 1.9ms | 2.1% | 1 | 0 |
| 500 | 500 | 1.5ms | 3.0% | 0 | 0 |
| 1,000 | 1,000 | 1.4ms | 5.7% | 1 | 0 |
| 2,000 | 2,000 | 1.9ms | 13.5% | 2 | 0 |
| 4,000 | 3,988 | 9.1ms | 30.4% | 48 | 113 |

**초당 4,000건에서 커넥션 풀 대기가 처음 생겼고, 약 75초 간격으로 주기적이었다.**
캐시 키 1,000개가 워밍업 중 거의 동시에 채워져 유효시간 60초 뒤 함께 만료되기 때문이다.
재생성이 12,895회 일어났고 `키 1,000개 × 12분 30초 ÷ 60초 = 약 12,500회` 와 맞는다.

### 쿼리별 비용

```
                          인덱스 있음    인덱스 없음
첫 페이지 11개 가져오기      0.071 ms      17.71 ms
개수 세기 (활성 2,843개)     0.757 ms      14.37 ms
개수 세기 (활성   284개)     0.165 ms
좋아요 조회                 0.065 ms      25.48 ms
────────────────────────────────────────────────
요청 하나가 쓰는 DB 시간     0.89 ms       57.6 ms      65배
```

인덱스가 있으면 셋 다 `Index Only Scan` 이고 없으면 셋 다 `Parallel Seq Scan` 이다.
인덱스 없는 쪽은 2026-09-27 에 트랜잭션 안에서 인덱스를 지우고 재고 되돌려 얻었다.

개수 세기를 두 크기로 재서 두 점을 이으면 **세는 시간 = 0.1ms + 댓글당 0.00023ms** 다.
**인덱스는 찾는 것은 줄이지만 세는 것은 못 줄인다.** 첫 페이지는 11개만 읽고 멈추는데 개수 세기는 전부 읽어야 한다.

쿼리 하나만 재면 65배인데 부하를 걸면 20배로 줄어든다. **부하가 걸리면 인덱스가 있어도 DB 가 느려진다.**

### 부하 생성기가 오염됐는지 보는 법

두 가지로 본다.

```
① 가상 사용자가 상한(3,000)에 닿았나
   닿기 전에 드롭이 시작되면 서버 한계다.  결과를 쓸 수 있다
   닿은 뒤에 드롭이 급증하면 k6 한계다.  그 계단은 버린다

② k6 가 본 응답시간과 앱이 본 응답시간이 벌어졌나
   벌어진 차이는 서버 밖에서 생긴 시간이다.  즉 k6 자신이 느려진 몫이다
```

②가 ①보다 빠르게 잡힌다. 2026-09-27 구간 A 에서 이렇게 나왔다.

```
초당 125건   k6 104ms    앱 102.7ms     거의 같다.  깨끗하다
초당 150건   k6 3,552ms  앱 1,440.7ms   2.5배 벌어졌다.  오염됐다
```

앱이 본 응답시간은 Prometheus 의
`increase(http_server_requests_seconds_sum[120s]) / increase(http_server_requests_seconds_count[120s])`
로 계단마다 얻는다.

**그리고 이 일이 실제로 일어났다.** 2026-09-25 에 캐시와 분산락을 켜고 재는데
초당 4,000건 계단에서 k6 가 가상 사용자를 평균 2,653명(상한 3,000) 썼다.
서버가 느려지자 k6 가 사용자를 늘리고, 늘어난 k6 가 서버 몫의 CPU 를 가져가 서버가 더 느려졌다.
그 계단의 처리량 3,574건과 p95 987.51ms 는 못 쓰는 값이다.

**그래서 AWS 에서는 k6 를 앱과 다른 인스턴스에 둔다.** 2026-09-18 에 AWS 를 택한 이유가 원래 이것이었고
(`로컬은 k6·앱·DB 가 같은 머신 자원을 나눠 쓴다`) 09-25 에 숫자로 확인됐다.

## 측정을 두 번 한다

같은 구간을 두 가지 방식으로 잰다. 답하는 질문이 다르다.

| | 어떻게 | 무엇을 아나 |
|---|---|---|
| **한계점 찾기** | 구간마다 시작값을 다르게 줘서 계단으로 올린다 | 어디서 무너지나. 몇 배 늘었나 |
| **같은 조건 비교** | 네 구간 모두 초당 100건으로 고정 | 같은 부하에서 얼마나 다른가 |

한계점 찾기만 하면 구간마다 부하가 달라서 "같은 조건에서 비교했다"고 말할 수 없다. 같은 조건 비교만 하면 어디가 한계인지 모른다. **그래서 둘 다 한다.**

같은 조건 비교에 쓰는 초당 100건은 인덱스가 없는 구간도 버티는 값이다. 그래서 네 구간을 나란히 놓을 수 있다.

```bash
# 한계점 찾기 — 구간별 시작값은 아래 표를 따른다
k6 run -e START_RATE=25 k6/test3.js

# 같은 조건 비교 — 네 구간 모두 같은 명령
k6 run -e START_RATE=100 -e STEP_MULS=1 -e RAMP=10s -e STEP_HOLD=4m k6/test3.js
```

같은 조건 비교는 워밍업 1분을 먼저 돌려 버리고 4분 10초를 잰다.

올리는 시간을 10초로 짧게 두는 이유가 있다. 1분에 걸쳐 올리면 그 1분이 측정에 섞이는데, 구간마다 올라가는 모양이 달라서 비교가 흐려진다. **같은 조건 비교는 평지에서 재야 한다.**

## 모니터링

`monitoring/` 에 Prometheus 와 Grafana 설정이 있다. 2026-09-24 로컬 측정에 쓴 그대로다.

```bash
docker run -d --name prometheus -p 9090:9090 \
  -v $(pwd)/benchmark/monitoring/prometheus.yml:/etc/prometheus/prometheus.yml \
  prom/prometheus

docker run -d --name grafana -p 3000:3000 \
  -v $(pwd)/benchmark/monitoring/grafana/datasources:/etc/grafana/provisioning/datasources \
  grafana/grafana
```

`prometheus.yml` 의 `targets` 가 `host.docker.internal:8080` 인데 이건 맥북에서 컨테이너 안이 호스트를 가리키는 이름이다. **AWS 에서는 이 한 줄만 앱 서버 주소로 바꾼다.**

앱은 이미 `/actuator/prometheus` 로 지표를 내보내고 있어서 따로 열 것이 없다.

Grafana 는 `admin / admin` 으로 들어간다. 대시보드는 `4701`(JVM Micrometer)을 import 하면 되는데 커넥션 풀이 빠져 있어 따로 만들어야 한다.

### 볼 것

| 지표 | 왜 |
|---|---|
| `hikaricp_connections_active` | 풀별로 본다. 합계로 보면 읽기 풀만 꽉 찬 것을 놓친다 |
| `hikaricp_connections_pending` | 0 을 벗어나면 요청이 줄을 서기 시작한 것이다 |
| `hikaricp_connections_max` | 뜨자마자 확인한다. 설정이 안 붙으면 기본값 10 으로 돈다 |
| `http_server_requests_seconds_count` | 앱이 본 처리량. k6 가 센 값과 맞는지 |
| `jvm_memory_used_bytes` | 톱니 바닥이 올라가면 누수 |
| `jvm_gc_pause_seconds_sum` | 응답이 튈 때 GC 때문인지 가른다 |

`http_server_requests_seconds_bucket` 이 없어서 **Grafana 에서는 `p95` 를 못 낸다.** `p95` 는 k6 에서 가져온다.

## 측정 순서

**쓰기를 섞은 실행은 댓글을 실제로 만든다.** 로컬에서 50초를 돌렸더니 50건이 늘었다. 몇 분을 돌리면 수백에서 수천 건이 늘어 **다음 측정의 데이터량이 달라진다.**

그래서 순서를 고정한다.

```
1. A 읽기 → B 읽기 → C 읽기 → D 읽기      데이터가 안 바뀐다
2. 데이터 다시 만들기
3. C 쓰기 섞음
4. 데이터 다시 만들기
5. D 쓰기 섞음
```

**읽기만 하는 측정을 전부 먼저 끝내고, 쓰기는 마지막에 한다.**

## 결과 읽는 법

합격선은 두 개만 둔다.

```
http_req_failed    < 1%     에러가 나기 시작하는 지점
dropped_iterations < 100    부하를 못 만들어냈으면 그 결과는 못 쓴다
```

### 드롭이 났다고 무조건 못 쓰는 건 아니다

`dropped_iterations` 는 보내기로 한 요청인데 k6 가 못 보낸 횟수다. 원인이 둘인데 뜻이 정반대다.

```
vus 가 상한에 닿기 전에 드롭 시작   →  서버가 못 버틴 것. 결과를 쓴다
vus 가 상한에 닿은 뒤 드롭 급증     →  k6 가 못 따라간 것. 그 뒤 계단은 믿지 않는다
```

리포트에서 `vus` 와 `vus_max` 를 같이 본다. 둘이 붙었으면 k6 쪽이 한계다.

### 숫자를 부를 때 쓰는 이름

과거 성능 주장이 보류된 사유 중 하나가 **지표 이름을 바꿔 부른 것**이었다. `HTTP Request Rate` 를 `TPS` 로 적어서 무엇을 잰 건지 알 수 없게 됐다.

- k6 가 출력하는 이름을 그대로 쓴다. `http_req_duration p(95)`, `http_reqs rate`
- `TPS`, `응답속도`, `처리속도` 같은 말로 바꾸지 않는다
- 평균과 `p95` 를 섞지 않는다. 다른 값이다

**`p95`는 합격선으로 쓰지 않는다.** 계단마다 값을 적어서 선으로 본다. 300ms를 넘기 시작하는 계단을 한계로 본다.

### 계단별 `p95` 는 k6 요약에 바로 찍힌다 [2026-09-27 추가]

`k6/test3.js` 가 요청마다 지금이 몇 번째 계단인지 꼬리표를 붙이고 계단마다 기준선을 건다.
그래서 요약의 `THRESHOLDS` 칸이 이렇게 나온다.

```
http_req_duration{step:1000}
  ✓ 'p(95)<300' p(95)=211.4ms
  ✓ 'avg<300'   avg=68.1ms

http_req_duration{step:2000}
  ✗ 'p(95)<300' p(95)=452.1ms      ← 여기서 300ms 를 넘었다

step_reqs{step:1000}
  ✓ 'count>0' count=240000
```

**`✗` 가 처음 붙는 계단이 한계다.** 실행 전체 p95 하나만 보면 마지막 계단이 다 먹어버려서 이걸 알 수 없다.

오르막 구간은 `step:ramp` 로 따로 빠진다. 계단 값에 오르는 중인 요청이 섞이지 않는다.
`step_reqs` 는 계단마다 요청이 몇 건 갔는지다. 목표 요청률 × 평지 시간과 맞는지 보면
그 계단이 목표를 실제로 소화했는지 알 수 있다.

기준선을 넘겨도 측정이 실패한 게 아니다. **`✗` 는 값을 알려주는 표시로 쓴다.**

합격선으로 안 쓰는 이유가 있다. 나중에 기준을 바꾸고 싶어지면 다시 재야 한다. 값을 다 적어두면 기준만 바꿔서 다시 보면 된다.

300ms는 부트캠프 때 쓰던 값이다. 보통 API는 100~200ms를 본다. 그보다 느슨하다.

첫 계단은 빼고 본다. 앱이 막 떠서 아직 예열이 안 됐다. 자바가 코드를 빠르게 만들기 전이고 DB 연결도 다 안 만들어졌다.

## 캐시가 왜 비는지 확인하는 법

`[Cache Put]` 로그가 찍힌 횟수가 DB를 조회한 횟수다.

```bash
grep -c '\[Cache Put\]' <앱 로그>
grep -c '\[Cache Hit\]' <앱 로그>
```

읽기만 돌렸을 때와 쓰기를 섞었을 때를 비교하면 캐시가 왜 비는지 알 수 있다.

로컬에서 50초 동안 초당 1건씩 댓글을 쓰면서 재본 값이다.

```
댓글 생성      50건
Cache Put     51회
Cache Hit  2,667회
```

TTL이 1분이다. 그러니 시간이 지나서 캐시가 빈 건 많아야 한 번이다. 나머지 50번은 댓글을 쓸 때마다 캐시를 지웠기 때문이다.

캐시가 비는 주된 이유는 시간이 지나서가 아니라 글을 써서다. TTL을 조금씩 다르게 주는 방법(지터)으로는 이게 안 줄어든다. 지울 시점을 흩뿌려도 글 쓰는 건 그대로라서다.

측정할 때마다 아래를 `benchmark/` 에 저장한다. 파일 이름에 구간과 측정 종류를 넣는다.

| 무엇 | 형식 | 예 |
|---|---|---|
| k6 결과, 사람이 읽는 것 | 텍스트 | `aws-A-limit.txt` 한계점 찾기, `aws-A-fixed.txt` 같은 조건 비교 |
| k6 결과, 기계가 읽는 것 | JSON | `aws-A-limit.json`. `--summary-export` 가 만든다. 계단별 `p95` 와 요청 수가 들어 있다 |
| 앱 지표, 측정 앞뒤 | 텍스트 | `metrics-A-before.txt`, `metrics-A-after.txt`. `/actuator/prometheus` 를 그대로 받는다 |
| 실행계획 | 텍스트 | `explain-aws-before.txt`, `explain-aws-after.txt` |
| 앱 로그 | 텍스트 | `log-aws-C.txt`. `[Cache Put]` 과 `[Cache Hit]` 횟수를 세는 데 쓴다 |
| 환경 스냅샷 | Markdown | 인스턴스 종류, 데이터 건수, **측정 시각** |

**앱 지표를 측정 앞뒤로 두 번 받는 이유가 있다.** Hikari 와 JVM 지표는 앱을 띄운 뒤로 계속 누적된다.
끝나고 한 번만 읽으면 워밍업과 조용했던 계단까지 섞인 평균이 나온다.
뒤에서 앞을 빼면 그 구간만의 값이 된다. 2026-09-25 에 이걸 안 해서
`무너질 때 DB 커넥션도 한계였나` 를 판정하지 못했다.

옛 표에는 `k6 결과 | HTML` 로 적혀 있었으나 현재 `k6/test3.js` 는 HTML 을 만들지 않는다. 지웠다.

**측정 시각을 꼭 적는다.** 나중에 "이 숫자들이 같은 날 같은 환경에서 나왔다"를 말할 근거가 된다. 과거 캡처가 보류된 이유가 그걸 증명할 수 없어서였다.

앱 서버가 2대면 로그를 각각 받는다. `scp` 로 가져온다.

맥북에서 돌린 결과는 커밋하지 않는다. `.gitignore` 에 규칙이 있다.
